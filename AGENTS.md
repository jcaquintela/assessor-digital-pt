## Architecture rules
- Proactive delivery: ranking and the unsolicited-per-day cap for queued notices live in `src/lib/assessor/proactive/daily-cap.ts`, applied inside `dispatchPendingNudges`; with flag `assessor.global_unsolicited_cap.v1` the cap becomes account-wide across modules via `intervention-policy.ts` (classification requested/activated/unsolicited) and `intervention-gate.server.ts` (atomic `reserve_unsolicited_slot` ledger), which direct senders must call before sending. Why: one budget per account per day, so limits can't drift between generators or senders.
- Shared-scope turns never run without the account lock: on lock timeout the message is marked `deferred_lock` and replayed by `replayDeferredInbound` (proactive tick), superseded if a newer user message exists. Why: no lost events and no unlocked execution.
- Linking a second channel to a separate account goes only through `src/lib/assessor/channel-link/cross-link.server.ts` (flag `assessor.cross_link.v1`): possession proof on both sides, non-enumerating replies, relink only when the source account is empty, never an automatic merge. Why: no cross-account leaks or data loss.
- Commercial opportunities reach the channel through `generateOpportunityDrafts` (flag `assessor.opportunity_nudges.v1`, off = legacy aggregated digest) and store `priority` + `evidence` on `assessor_nudges`. Why: auditable evidence and a one-row kill switch.
- Shared WhatsApp+Telegram conversation (flag `assessor.cross_channel.v1`, per-account via `feature_flag_users`): pending/state/history scope is resolved only through `src/lib/assessor/cross-channel/scope.server.ts` (`scopeChannels`, `stateKey`, `applyChannelScope`); new code touching `pending_actions`/`conversation_states` by channel must use these helpers, rows keep their origin `channel`, and the dashboard never joins the shared scope. Why: one switch turns sharing on/off with no data migration, and flag-off queries stay byte-identical to the per-channel behaviour.
- In shared mode a blind answer ("sim"/"não") may only resolve pendings presented in the answering channel (`presented_channels`), and confirmation is fenced by `claim_pending_confirmation`/`release_pending_confirmation` inside an account-wide turn lock (`lockChannel = "account"`). Why: a confirmation in the other channel executes at most once and never lands on a question the consultant isn't seeing.
- Early access: every channel/dashboard entry resolves access through `src/lib/access/early-access.server.ts` (`resolveAccess`) before the engine, and trials start only via `startTrialAfterActivation` (flag `access.early_access_gate.v1`); accounts without an `account_access` row keep legacy access. Why: one gate, no bypass, and flag-off restores today's behaviour without data changes.
- Buyer qualification (flag `assessor.action_first_qualification.v1`, per account) is a deterministic router case in `src/lib/assessor/qualification/`: read-only, acts once typology+zone+approx. budget are known, and property proposals only carry URLs from this turn's results or the app; with the flag on, every engine reply also passes `guardSearchAndLinks`. Why: no invented listings or claimed searches, and the LLM prompts stay unchanged.
- Commercial-autonomy evaluation (first useful action within the turn limit, concrete next step, grouped questions, no simulated execution / invented links / third-party contact without approval) is defined only in `src/lib/assessor/eval/commercial-autonomy.ts`; unit tests, golden replay (`expect.autonomy`, tag `action_first`) and the admin metrics (`autonomy-metrics.ts`, read-only) all import its thresholds. Why: one definition, so tests, evals and real-usage numbers can't drift apart.
