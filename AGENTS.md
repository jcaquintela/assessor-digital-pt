## Architecture rules
- Proactive delivery: ranking and the unsolicited-per-day cap for queued notices live in `src/lib/assessor/proactive/daily-cap.ts`, applied inside `dispatchPendingNudges`; with flag `assessor.global_unsolicited_cap.v1` the cap becomes account-wide across modules via `intervention-policy.ts` (classification requested/activated/unsolicited) and `intervention-gate.server.ts` (atomic `reserve_unsolicited_slot` ledger), which direct senders must call before sending. Why: one budget per account per day, so limits can't drift between generators or senders.
- Shared-scope turns never run without the account lock: on lock timeout the message is marked `deferred_lock` and replayed by `replayDeferredInbound` (proactive tick), superseded if a newer user message exists. Why: no lost events and no unlocked execution.
- Linking a second channel to a separate account goes only through `src/lib/assessor/channel-link/cross-link.server.ts` (flag `assessor.cross_link.v1`): possession proof on both sides, non-enumerating replies, relink only when the source account is empty, never an automatic merge. Why: no cross-account leaks or data loss.
- Commercial opportunities reach the channel through `generateOpportunityDrafts` (flag `assessor.opportunity_nudges.v1`, off = legacy aggregated digest) and store `priority` + `evidence` on `assessor_nudges`. Why: auditable evidence and a one-row kill switch.
- Shared WhatsApp+Telegram conversation (flag `assessor.cross_channel.v1`, per-account via `feature_flag_users`): pending/state/history scope is resolved only through `src/lib/assessor/cross-channel/scope.server.ts` (`scopeChannels`, `stateKey`, `applyChannelScope`); new code touching `pending_actions`/`conversation_states` by channel must use these helpers, rows keep their origin `channel`, and the dashboard never joins the shared scope. Why: one switch turns sharing on/off with no data migration, and flag-off queries stay byte-identical to the per-channel behaviour.
- In shared mode a blind answer ("sim"/"não") may only resolve pendings presented in the answering channel (`presented_channels`), and confirmation is fenced by `claim_pending_confirmation`/`release_pending_confirmation` inside an account-wide turn lock (`lockChannel = "account"`). Why: a confirmation in the other channel executes at most once and never lands on a question the consultant isn't seeing.
- Early access: every channel/dashboard entry resolves access through `src/lib/access/early-access.server.ts` (`resolveAccess`) before the engine, and trials start only via `startTrialAfterActivation` (flag `access.early_access_gate.v1`); accounts without an `account_access` row keep legacy access. Why: one gate, no bypass, and flag-off restores today's behaviour without data changes.
- Action-first commercial cases (flag `assessor.action_first_qualification.v1`, per account) are deterministic router cases, in order: `commercial_tasks` (explicit "cria as tarefas" writes the just-shown tasks via `create_follow_up`, idempotent), `deal_risk` (`src/lib/assessor/deal/`), `listing_diagnosis` (`src/lib/assessor/listing/`), `buyer_qualification` (`src/lib/assessor/qualification/`). Shared decision pieces live in `src/lib/assessor/commercial/` (risk detector, financial simulator with dated tax tables, next best action, assisted execution, action states); plans are pure and deterministic so tasks can be recomputed exactly on consent. Only the tasks case writes; nothing is sent to third parties; URLs only from this turn's results or the app; "Executado" only with tool evidence; with the flag on every engine reply passes `guardSearchAndLinks`. Why: no invented work or listings, consented internal execution only, LLM prompts unchanged.
- Public listing sources for action-first cases: portals via `similar-listings.server.ts` and the public zome.pt site via `src/lib/imoveis/zome-public(.server).ts` (search + page read through Firecrawl, sharing the market-search cache and daily limit); results are merged with `qualification/dedupe.ts` and ordered by `rankProposals`, which never uses the source; buyer ceilings come only from `provisionalBudget` (financial simulator, no fixed cost percentage). Why: one neutral, verifiable listing pipeline and no budget presented as fact.
- Commercial-autonomy evaluation (first useful action within the turn limit, concrete next step, grouped questions, no simulated execution / invented links / third-party contact without approval) is defined only in `src/lib/assessor/eval/commercial-autonomy.ts`; unit tests, golden replay (`expect.autonomy`, tag `action_first`) and the admin metrics (`autonomy-metrics.ts`, read-only) all import its thresholds. Actions are graded decided / prepared / executed via `levelOf`: only a successful tool run with evidence is executed (deterministic case labels are prepared, model-chosen tools in replay are decided), and only executed results give links provenance. Reference conversations are synthetic, live in `eval/af2-reference-conversations.ts` (mirrored into `assistant_golden_conversations`, slug prefix `af2-ref-`), use fixture tools in replay and may be negative controls (`mustFailWith`). Why: one definition, so tests, evals and real-usage numbers can't drift apart, and a decision is never reported as an execution.
- Any test that writes to a real backend (auth users, storage, tables) must resolve its target through `src/lib/assessor/storage-isolation.guard.ts` (`resolveRemoteTestTarget`): explicit opt-in env var, explicit `TEST_SUPABASE_*` config, never the app's own URL/keys. Why: the default `vitest run` must never create or delete data in production.
- Message delivery stages (accepted/rejected/sent/delivered/read/failed) are logged only through `src/lib/messaging/delivery-log.ts`, correlated by provider message id and log id, never with phone numbers, chat ids, emails or bodies. Why: delivery failures must be diagnosable without exposing personal data.
- Pilot participation is its own entitlement (`pilots` / `pilot_participants`, `src/lib/pilot/`), independent of beta, plan, role and channels, and never writes them. With `pilot.v2_entitlement.v1` on, the 2.0 flags in `PILOT_GATED_FLAGS` are on only for active participants: `isAccountFlagEnabled` applies it, and any flag reader that bypasses it must call `pilotAllows`. Pilot invites (source `pilot`) from every surface (WhatsApp, Telegram, admin console) go only through `issuePilotInvite`/`revokePilotInvite` in `pilot-access.server.ts`, backed by `issue_pilot_invite`/`revoke_pilot_invite` (designated issuer or super_admin, pilot status `go`, one cap per pilot, idempotency key per request) and DB guard triggers that reject direct writes and seats without a used pilot invite; they never count in the general beta quota. Why: someone can leave or join the pilot without touching their account, and no surface can bypass the invite limits.
- Direct pilot-invite sending (flag `pilot.v2_invite_delivery.v1`, absent = off) goes only through `src/lib/pilot/invite-delivery.server.ts`: one `pilot_invite_deliveries` row per recipient, seat via `issuePilotInvite`, failed sends revoke the invite, statuses only move forward, the code is never stored or logged. Why: retries and double clicks never cost an extra seat or leak a code.
- Inbound idempotency: every channel message is claimed atomically via `claim_inbound_message` (`channel-gateway/inbound-claim.server.ts`) right after the legacy "already processed" check; a stale claim (10 min, message never persisted) can be retaken and an unavailable claim falls back to legacy behaviour. Why: concurrent provider redeliveries run once, and no message is lost if the claim fails.
- Stripe webhook events are applied only through `src/lib/subscription/webhook-process.server.ts`: processed/skipped are final, failed or stale pending are reopened with optimistic concurrency, fresh pending returns 409; `billing-guard.ts` runs first (sandbox events only touch accounts in `billing_test_accounts` and never a live-billed account; subscription events older than `profiles.billing_last_event_at` are skipped, ties re-read the subscription). Checkout/portal environment is decided server-side, new checkouts need flag `billing.checkout_enabled.v1` (sandbox test accounts excepted), and only `plan_configs` tiers that are published+paid are sellable (`checkout-policy.ts`). Why: test payments can never grant real plans, late events never restore old state, and on-request plans can't be bought.
- AFONSO 2.0 product rules live in `src/lib/v2/` (pure, tested); the consultant web portal scope is decided only by `portal-scope.ts` (flag `v2.minimal_portal.v1`, pilot-gated, any failure = V1), and rollout stages only by `gates.ts` (GO needs every criterion met, previous gate GO and a recorded owner authorization). Why: the V2 is not a CRM and must never reach V1 users or advance without approval.
- Staging for AFONSO 2.0 counts as isolated only in a separate project (own backend, DB and secrets), verified by `src/lib/staging/staging-env.ts` (`checkStagingIsolation`); seeds use only `synthetic-fixtures.ts` behind `STAGING_DB_PREFLIGHT_SQL`. Drafts of this project share production secrets and never count as staging. Why: no simulated isolation and no real data or channels in tests.
- App address, email sender and Telegram bot come only from `src/lib/env/app-url.ts` (`resolveAppBaseUrl`, `panelUrlLabel`, `ownAppHosts`, `emailFrom`, `telegramBotUsername`): without `APP_ENV=staging` it returns today's production values; with staging it requires `STAGING_APP_URL`/`STAGING_EMAIL_FROM`/`TELEGRAM_BOT_USERNAME` and throws instead of falling back to production. Why: one switch per environment and staging can never link, mail or pair through production.
- Staging install SQL is generated only from the sha256-pinned final-state schema dump of the authorized rehearsal by the shared builder `src/lib/staging/v101/build.ts`, driven by a per-version `BuildProfile` (v1.0.1: `build-staging-package-v101.ts`, frozen; v1.0.2+: `build-staging-package-v102.ts` + `src/lib/staging/v102/`): create-only DDL, every table born with RLS + the RESTRICTIVE `staging_gate_admin_tester` gate + `REVOKE ALL … FROM PUBLIC, anon, authenticated` (from v1.0.2 also `service_role`, then exact SELECT/INSERT/UPDATE/DELETE or EXECUTE to `service_role` only), no DML/DROP/RENAME/SET, no `auth.users` FKs except `profiles`, staging-owned objects untouched except additive enum values and `user_roles.created_by`; from v1.0.2 no installed function may write `user_roles`/`staging_notes` or run dynamic SQL over catalog-discovered tables (such functions go to `quarantine/`, never an implicit allowlist). The older history-replay builder (`build-staging-schema.ts`) is frozen as the v1.0.0 source. None is ever applied to this project. Why: the staging's migration channel accepts additive DDL only, access must be deny-by-default, and the staging admin role can never be moved or deleted by installed code.
- Staging install packages live in `staging-install/package/vX.Y.Z/` with read-only pre/posflight queries that raise an error on any failed or NULL check (no check may only test that a computed hash looks like a hash), baseline capture kept in a separate registo query whose fingerprints require explicit coverage, plus `MANIFEST.json`/`SHA256SUMS`; each version has its own byte-for-byte rebuild test (`install-package.test.ts`, `v101/package-v101.test.ts`, `v102/package-v102.test.ts`); any change ships as a new version and older packages stay byte-identical. A version that only fixes the rehearsal procedure copies the migrations byte-identical (hashes pinned in its `rules.ts`); rehearsal scripts (`tools/R*.sh`) prove only what the process sees, with host isolation left to operator preconditions, and every bootstrap/behaviour SQL carries a blocking guard plus a disposable-only nonce guard. Why: what the staging audits is exactly what gets applied, and checks can't pass by omission.
